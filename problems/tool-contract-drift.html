Tools & Integrations

{} The tool still responds, but its contract quietly changed

Schema and semantic drift can break agent behavior without producing a clean infrastructure failure.

What it looks like

  • Tool calls return 200 but fields are missing, renamed or interpreted differently.
  • The model starts repairing tool errors in free text.
  • A provider version change causes a sudden rise in retries or fallback behavior.

Why this happens

Agents depend on more than endpoint availability. They depend on stable argument names, enums, error semantics and response meaning. A tool can remain reachable while its contract changes underneath the agent. Because LLMs are flexible, they may partially adapt instead of failing fast, which turns a clear integration break into inconsistent behavior.

A simple real-world example

A shipping tool used to return `delivered=true|false`. A new version returns `status='delivered'|'in_transit'|'exception'`. The integration layer passes the new response through without validation. The model sees the word 'delivered' in examples from older traces and incorrectly treats some `in_transit` responses as completion.

What teams usually get wrong

  • Using raw provider responses directly as model context.
  • Treating HTTP availability as contract health.
  • Allowing schema validation errors to be repaired only by the LLM.
  • Rolling out tool changes without replaying representative agent traces.

What I would put in production

  • Put stable typed adapters between agents and external APIs.
  • Validate both request and response schemas outside the model.
  • Version tool contracts and publish compatibility windows.
  • Map provider errors into stable internal error classes.
  • Run tool-call regression tests before provider or schema upgrades.

What I would monitor

schema validation failures
unknown enum values
tool retry/fallback rate
behavior changes by tool version

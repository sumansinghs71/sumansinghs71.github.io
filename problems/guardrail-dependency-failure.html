Safety & Security

🛡 The safety layer failed because its dependency failed

A guardrail is only a control if its failure semantics are explicit.

What it looks like

  • Safety checks time out while the core agent remains healthy.
  • Teams are forced to choose between blocking all work and bypassing the control.
  • Different services handle the same guardrail outage differently.

Why this happens

Guardrails often depend on policy services, identity, classifiers or external APIs. When that dependency fails, the architecture must already know whether each action fails closed, degrades to a safer mode, or can continue.

A simple real-world example

A tool-enabled agent must pass a policy check before sending an external message. The policy dependency becomes unavailable. If the runtime treats “no decision” as “allow,” a dependency outage silently removes the control.

What teams usually get wrong

  • Implementing fail-open accidentally through generic exception handling.
  • Using one failure policy for both low-risk reads and irreversible writes.
  • Letting the model decide whether a missing guardrail can be skipped.
  • Monitoring guardrail decisions but not guardrail availability.

What I would put in production

  • Define fail-closed/degraded behavior per action risk tier.
  • Keep authorization enforcement outside the model.
  • Cache only policies whose staleness bounds are explicitly safe.
  • Add independent kill switches for high-impact actions.
  • Exercise guardrail dependency outages in release tests.

What I would monitor

guardrail availability
no-decision/error rate
blocked high-risk actions
degraded-mode duration
Takeaway: A missing safety decision is not an approval.

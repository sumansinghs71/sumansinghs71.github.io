Runtime & SandboxProduction failure pattern

∞The LLM stopped calling. The tool never did.

Model-call limits protect the outer agent loop. They do not stop code that is already running forever inside a sandbox.

LLM→tool call #1→sandbox→while (true)
Outer loop: 1 call. Inner execution: unbounded.
Signals in production
  • One tool invocation stays in-flight while the LLM-call counter stops moving.
  • Sandbox CPU, memory, process count or output keeps growing.
  • User cancellation returns, but the tool process or its children keep running.
Failure boundary

The hand-off from orchestrator → executable process. Once code is running, model-step limits no longer own termination.

01

Why it happens

Agent runtimes usually cap model turns, tokens or tool calls. Those controls help when the model repeatedly asks for more work. A single tool call is different: generated code can deadlock, recurse, block on I/O, spawn children, flood stdout or loop forever without making another LLM request.

02

Production-shaped example

A code tool runs generated Python containing a retry loop with no terminal condition. The agent has a 20-call budget, but it used only one call. The sandbox burns a CPU core for an hour because the component that owns the LLM budget is not the component that owns the process.

What fooled the team

First 5 minutes
  1. Find the sandbox/container and current process tree.
  2. Check wall-clock age, CPU time, RSS, output bytes and last progress heartbeat.
  3. Terminate through the supervisor; if the tool can write externally, reconcile side effects before retry.
03

Controls

Prevent the failure, detect it early, then recover without making it worse.

PREVENT
  • Run executable code in a separate process/container with an external supervisor.
  • Enforce per-invocation wall-clock TTL plus overall task deadline.
  • Apply CPU, memory, PID/thread, file-descriptor, disk, output and network budgets at the sandbox boundary.
  • Prefer narrow typed tools when arbitrary code execution is not required.
DETECT
  • Emit heartbeat/progress events for long-running tools and alert on progress silence.
  • Track wall time and CPU time per invocation, not only model/tool-call counts.
  • Record code/tool hash and process-tree metadata so repeated hangs can be quarantined.
RECOVER
  • TERM → bounded grace period → KILL the entire process group/container.
  • Destroy a hard-timed-out sandbox instead of returning it to the pool.
  • Return an explicit TOOL_TIMEOUT/TOOL_KILLED state; never disguise it as a normal tool response.
Prove it with failure injection
  • tight CPU loop
  • blocked network call
  • unbounded stdout
  • child-process storm
  • side effect commits, then tool hangs

PRODUCTION INVARIANTEvery tool invocation has an owner outside the tool that can terminate its full process tree within a bounded time.

An agent-step limit controls the agent. A sandbox deadline controls the code. Production needs both.

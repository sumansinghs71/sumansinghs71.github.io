Reliability & Runtime

∞ The LLM stopped calling. The tool never did.

Model-call limits can stop an agent loop, but they do not stop generated code or a tool process that loops forever inside a sandbox.

What it looks like

  • The orchestration layer shows one tool call in-flight for minutes while the LLM call count stays below its configured limit.
  • The sandbox consumes CPU or memory continuously, but no new model or tool invocation is recorded.
  • The user cancels the task, yet the child process continues running until the worker or container is killed.

The failure boundary

The dangerous boundary is the hand-off from the agent runtime to executable code. Before the call, the orchestrator owns termination. After the call starts, a model-step limit is irrelevant unless a separate sandbox supervisor can independently stop the process.

Why this happens

Teams often protect the outer loop with max model calls, max agent steps, token budgets or API-level limits. Those controls help when the model repeatedly invokes tools. They do not help when a single invocation starts code containing an infinite loop, deadlock, blocking network call, runaway recursion, child-process storm or unbounded output. From the orchestrator's point of view there may be only one perfectly valid tool call that never returns.

A production-shaped example

A code-execution tool receives generated Python that retries an empty work queue with `while True`. The agent made only one tool call, so its 20-call budget never moves. The sandbox process keeps one CPU core busy for an hour. A model-side stop condition cannot see or terminate the loop because execution has already crossed into a different process boundary.

What fooled the team

  • Relying on a maximum number of LLM calls or agent steps as the primary loop control.
  • Assuming an HTTP 4xx/5xx limit from the model gateway protects code that is already running.
  • Sending a cancellation flag to the model while leaving the sandbox process tree alive.
  • Using a cooperative timeout inside generated code as the only termination mechanism.

Prevent

  • Run generated or untrusted code in a separate process/container, never in the agent worker process.
  • Enforce an external wall-clock TTL per tool invocation and an overall task deadline.
  • Apply CPU-time, memory, PID/thread, file-descriptor, disk, output-byte and network-request limits at the sandbox boundary.
  • Prefer narrow deterministic tools over arbitrary code execution when the task does not require a general sandbox.
  • Pass cancellation/deadline context to well-behaved tools, but treat it as an optimization rather than the hard safety boundary.

Detect

  • Track wall-clock duration and CPU seconds for every in-flight tool invocation.
  • Require heartbeat or progress events for long-running tools and alert on progress silence.
  • Watch sandbox RSS, process count, output growth and child-process tree—not only LLM request count.
  • Record the code/tool hash so repeated hangs from the same artifact can be quarantined.

Recover

  • On deadline: send graceful termination, wait a short bounded grace period, then kill the entire process group/container.
  • Destroy the sandbox after a hard timeout rather than returning it to the pool in an unknown state.
  • Mark the workflow as TOOL_TIMEOUT or TOOL_KILLED instead of pretending the tool returned a normal error.
  • Before retrying a timed-out write-capable tool, reconcile whether an external side effect happened.
  • Cap retries and escalate or quarantine repeated executions of the same failing code.

Prove it with failure injection

  • A tight `while True` CPU loop.
  • Infinite recursion or uncontrolled memory growth.
  • A sleeping or blocked network call that never returns.
  • Unbounded stdout/log generation.
  • A child-process storm.
  • A tool that commits an external side effect and then hangs before returning.

What I would monitor

tool wall-clock p95/p99
CPU seconds per invocation
progress-heartbeat age
forced sandbox kills
timeouts retried after possible side effects
repeat hangs by code/tool hash

Production invariant

Every tool invocation has an owner outside the tool that can terminate its full process tree within a bounded time.
Takeaway: An agent-step limit controls the agent. A sandbox deadline controls the code. Production systems need both.

Quality & Evals

Δ The upgrade was compatible—until the agent actually ran

Schema compatibility does not guarantee behavioral compatibility across an agent workflow.

What it looks like

  • A dependency upgrade passes build and contract tests but a workflow fails at runtime.
  • A tool still accepts the same fields but behaves differently.
  • Only certain hosts, versions or execution paths fail.

Why this happens

Agent behavior depends on more than static interfaces. Runtime libraries, tool semantics, security policy, serialization, model behavior and environment state can change the path from planning to side effect even when the schema looks compatible.

A simple real-world example

A tool dependency is upgraded. The function signature is unchanged, so integration tests pass. Under one runtime path, serialization or policy behavior changes and the agent can no longer execute a previously valid action.

What teams usually get wrong

  • Equating successful compilation with agent compatibility.
  • Testing tools in isolation but not end-to-end workflows.
  • Upgrading every worker simultaneously.
  • Keeping no replayable examples of previously successful runs.

What I would put in production

  • Maintain state-verified workflow regression tests.
  • Record environment, model, tool and policy versions with each run.
  • Canary upgrades against representative workflows.
  • Compare downstream state, not only text output.
  • Keep rollback paths for runtime and dependency changes.

What I would monitor

workflow regression rate
version-specific failures
state-verification mismatch
rollback frequency
Takeaway: Software compatibility is necessary. Agent behavioral compatibility must still be tested.

Safety & Security

✓? The approval was real, but the world changed before execution

Human approval is not a permanent permission slip. The state being approved can become stale.

What it looks like

  • An action executes hours after it was approved.
  • The amount, account, policy or target changed between review and execution.
  • The approver saw one plan, but the agent executed a later version.

Why this happens

Approval flows often capture a simple yes/no decision, but production actions are about a specific state: this amount, this resource, this plan, at this time. Long-running agents create a gap between review and execution. If the runtime does not bind approval to the exact action and revalidate important state, a valid approval can authorize something the person never actually reviewed.

A simple real-world example

An agent prepares a $5,000 vendor payment and a manager approves it at 10:00 AM. Before execution, the invoice is amended to $8,500 after new data arrives. At 11:00 AM the agent continues the workflow and uses the old approval because the task ID is unchanged. The manager approved the workflow, but not the new amount.

What teams usually get wrong

  • Binding approval only to a task or conversation ID.
  • Allowing the agent to edit high-risk parameters after approval.
  • Reusing approvals after long pauses or resumes.
  • Treating 'approved once' as 'approved forever.'

What I would put in production

  • Bind approvals to a hash/version of the exact action parameters.
  • Expire approvals for time-sensitive operations.
  • Revalidate critical state immediately before execution.
  • Request approval again when risk-relevant fields change.
  • Record who approved what version and what actually executed.

What I would monitor

approval-to-execution delay
actions changed after approval
expired approval attempts
reapproval rate after resume

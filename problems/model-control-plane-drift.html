Model & Control Plane

404 The model existed in config. The provider said 404.

Your control plane can say a deployment is active after the provider has removed, renamed or retired the actual serving resource.

What it looks like

  • Agents repeatedly request a model deployment that no longer exists.
  • Database or configuration records still show the model as enabled.
  • The failure persists across application restarts because the wrong state is durable.

The failure boundary

Two control planes disagree: your catalog says 'available' while the provider's serving plane says 'not found'. The application cannot repair that contradiction with retries.

Why this happens

Model catalogs are often copied into databases, feature flags and agent configuration. Provider-side changes happen independently. Without reconciliation, stale control-plane state can outlive the deployment it references.

A production-shaped example

A team removes an old dedicated model deployment during a migration, but several agents still reference its deployment key in durable configuration. Every request gets a deterministic 404. Retries increase load but cannot recreate a resource that no longer exists.

What fooled the team

  • Retrying a deterministic 'deployment not found' error.
  • Validating model configuration only when an agent is created.
  • Treating database state as the source of truth for provider inventory.
  • Deleting an old deployment before proving zero active references.

Prevent

  • Maintain a reconciler between internal model catalog state and provider inventory.
  • Block deletion/retirement while active references remain.
  • Validate deployment existence during release and agent activation.
  • Use staged deprecation: announce, migrate, drain, verify, then remove.

Detect

  • Alert on deterministic model-not-found errors separately from transient failures.
  • Continuously compare configured deployment IDs with provider inventory.
  • Track active agents by deployment/version before migration.

Recover

  • Stop retrying the missing deployment.
  • Route to a pre-validated compatible deployment when policy allows.
  • Repair the control-plane reference and verify all consumers converge.

Prove it with failure injection

  • Remove a test deployment while references still exist and verify the reconciler catches it.
  • Rename/version a deployment and confirm pre-release validation blocks stale references.
  • Exercise rollback to the previous valid deployment mapping.

What I would monitor

configured-vs-provider drift
model-not-found errors
active references per deployment
retirement blockers
fallback activation

Production invariant

Every enabled model reference must resolve to a serving deployment that the runtime can actually call.
Takeaway: A model name in a database is not a serving model. Reconcile control-plane truth with provider truth.

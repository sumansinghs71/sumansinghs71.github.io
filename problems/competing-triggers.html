Tools & Integrations

⇉ Two valid triggers started processing the same work.

A webhook and a poller can both be correct individually and still create duplicate or conflicting execution paths together.

What it looks like

  • Users receive duplicate actions or replies.
  • One consumer makes work disappear before the intended consumer sees it.
  • Disabling either trigger makes the problem vanish.

The failure boundary

The failure is ownership. Two independently valid consumers both believe they are responsible for the same external event.

Why this happens

Teams often add a faster event path without fully retiring the old scheduled path. If both consume the same mailbox, queue, record or status transition, timing decides which workflow wins. Idempotency helps, but the architecture still needs an explicit owner.

A production-shaped example

A scheduled poller is designed to process unread requests every few minutes. Later, a real-time webhook is enabled for the same source. The webhook responds first and changes the source state; when the poller runs, the item no longer matches its query—or both paths perform separate side effects.

What fooled the team

  • Assuming two consumers are safe because both are individually idempotent.
  • Using source state such as 'unread' as the only ownership mechanism.
  • Renewing obsolete subscriptions automatically.
  • Failing to record which trigger claimed an event.

Prevent

  • Choose one authoritative ingestion path per event class, or explicitly coordinate multiple paths.
  • Assign a stable event ID and durable deduplication record.
  • Use leases/fencing or an inbox table when only one consumer may own work.
  • Make trigger lifecycle visible and auditable.

Detect

  • Trace event ID across every trigger and consumer.
  • Alert on multiple claims for the same event.
  • Inventory active webhooks, pollers and schedules continuously.

Recover

  • Disable the unintended path and stop automatic renewal.
  • Reconcile external side effects before replaying missed events.
  • Backfill from the source of truth with dedupe enabled.

Prove it with failure injection

  • Fire webhook and poller simultaneously for the same event.
  • Delay one consumer so ordering reverses.
  • Restart a consumer after claim but before completion.

What I would monitor

duplicate event claims
active trigger inventory
dedupe hits
ownership conflicts
replayed events

Production invariant

For every external event, the system can identify the single execution owner—or prove that multiple consumers are safe.
Takeaway: Two correct pipelines can make one incorrect system when ownership is implicit.

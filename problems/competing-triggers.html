Event OwnershipProduction failure pattern

⇉Two valid triggers started processing the same work.

A webhook and a poller can each be correct and still create duplicate or conflicting execution together.

event→webhook→same work→poller
Two ingestion paths, one piece of work.
Signals in production
  • Duplicate replies/actions appear for the same source event.
  • One consumer makes the item disappear before another sees it.
  • Disabling either path removes the bug.
Failure boundary

Ownership is implicit: two consumers independently believe they own the same external event.

01

Why it happens

Real-time triggers are often added before scheduled paths are fully retired. If both watch the same mailbox, queue or record transition, timing determines which workflow wins. Idempotency reduces damage, but ownership still needs to be explicit.

02

Production-shaped example

A poller processes unread requests every few minutes. Later a webhook is enabled for the same source. The webhook handles the item first and changes its state; the poller either misses it or performs a second side effect.

What fooled the team
“both consumers are idempotent”source state such as unread = ownershipauto-renewing old subscriptions
First 5 minutes
  1. Trace the same event ID across every ingestion path.
  2. Disable the unintended owner before replaying anything.
  3. Reconcile already-produced side effects, then backfill with dedupe enabled.
03

Controls

Prevent the failure, detect it early, then recover without making it worse.

PREVENT
  • Choose one authoritative ingestion path per event class—or coordinate ownership explicitly.
  • Use stable event IDs plus a durable inbox/dedupe record.
  • Use leases/fencing when only one worker may own the event.
  • Inventory webhook, poller and schedule lifecycle centrally.
DETECT
  • Alert on multiple claims for one event ID.
  • Trace trigger → claim → side effect end-to-end.
  • Continuously inventory active subscriptions and schedules.
RECOVER
  • Disable/expire the unintended trigger.
  • Reconcile side effects before replay.
  • Backfill from source of truth through the dedupe path.
Prove it with failure injection
  • webhook and poller fire simultaneously
  • reverse ordering with delay
  • consumer dies after claim
  • subscription unexpectedly reappears
Monitor
duplicate claimsactive triggersdedupe hitsownership conflictsreplayed events
PRODUCTION INVARIANTEvery external event has one identifiable execution owner—or the system can prove multiple consumers are safe.

RAG & SearchProduction failure pattern

ΣOne RAG flag turned a small question into thousands of clauses.

Hybrid retrieval can fail before retrieval begins when rewrites, filters and expansions multiply into an oversized search plan.

1 question→rewrites × filters→3000+ clauses→search rejects
The input is small. The generated plan is not.
Signals in production
  • Search fails on a query-complexity/clause limit.
  • Only specific tenants, filters or feature flags trigger it.
  • A simpler retrieval path immediately works.
Failure boundary

Complexity is created after the user question but before the search engine: query planning becomes the failure point.

01

Why it happens

Hybrid search may combine query rewrites, lexical terms, vector searches, metadata filters, entitlements and synonyms. Multiplicative expansion can cross hard engine limits even when the original prompt is tiny.

02

Production-shaped example

A hybrid-retrieval flag enables several rewrites while a large entitlement filter expands into many Boolean terms. The final serialized search request exceeds the engine's complexity ceiling and is rejected before ranking.

What fooled the team
looking only at user-query lengthraising engine limits without bounding planninglogging the question but not the generated search request
First 5 minutes
  1. Capture the final serialized search plan and clause/filter counts.
  2. Identify which rewrite/filter stage multiplied complexity.
  3. Disable or bypass that stage and retry through a bounded fallback.
03

Controls

Prevent the failure, detect it early, then recover without making it worse.

PREVENT
  • Enforce a query-complexity budget before dispatch.
  • Cap rewrites, synonym expansion, filter cardinality and Boolean clauses.
  • Prefer set/lookup filters over giant OR lists where supported.
  • Provide a simpler retrieval fallback when the plan exceeds budget.
DETECT
  • Log clause count, rewrite count, filter cardinality and payload size.
  • Slice failures by feature flag, tenant and retrieval mode.
  • Alert before the hard engine limit, not only after rejection.
RECOVER
  • Retry with a bounded fallback query, never the same oversized request.
  • Disable the expansion path via a safe feature switch.
  • Store the failed query plan as a regression case.
Prove it with failure injection
  • max entitlement set
  • worst-case rewrite/synonym expansion
  • hybrid + high-cardinality filters
  • query-budget fallback
Monitor
clause countfilter cardinalityquery payload sizehard-limit errorsfallback rate
PRODUCTION INVARIANTNo generated retrieval plan reaches the search engine without passing a bounded complexity check.

Quality & Evals

↗ The new model is better overall—and worse for your workflow

Provider upgrades can improve benchmarks while changing tool choice, formatting, refusals or edge-case behavior that your product depends on.

What it looks like

  • General quality scores improve but one business flow degrades.
  • Tool-call arguments change shape or become more verbose.
  • A new model refuses cases the old one completed, or acts where the old one escalated.

Why this happens

Your application is not a benchmark average. It is a distribution of specific prompts, tools, policies, languages, failure cases and user behaviors. A model upgrade changes a dependency with a very large behavioral surface. Even if the API is compatible, the behavior is not guaranteed to be identical.

A simple real-world example

A claims agent moves from Model A to Model B. Overall answer quality rises. But Model B is more eager to call the document-search tool before checking the structured claims database. Latency rises, retrieval noise increases and a small but important set of claims starts using stale policy text. Nothing in the provider's API contract changed.

What teams usually get wrong

  • Testing only a few happy-path prompts.
  • Comparing average score without looking at important slices.
  • Changing the model, prompt and retrieval settings in the same release.
  • Assuming a provider's 'better model' means lower operational risk for every workflow.

What I would put in production

  • Run the golden dataset and production-derived regression set against both versions.
  • Compare tool trajectories, not only final answers.
  • Slice results by task, risk, tenant, language and failure type.
  • Canary the new model and keep a fast rollback path.
  • Change one major behavioral dependency at a time when possible.

What I would monitor

regression rate by slice
tool-choice drift
refusal/escalation drift
cost and latency change by task

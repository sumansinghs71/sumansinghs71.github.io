Reliability & Runtime

↘ The primary model hit capacity and the workflow stopped

A healthy application can still fail when inference capacity becomes the bottleneck and no degraded path exists.

What it looks like

  • Token or concurrency limits start rejecting requests.
  • Backlogs rise while application hosts remain healthy.
  • Humans suddenly become the fallback because no model fallback exists.

Why this happens

Inference is a capacity-constrained dependency. If every task requires one model/deployment and overload has no explicit degradation policy, capacity pressure becomes a full workflow outage.

A simple real-world example

A document-processing agent uses a high-capability deployment for every request. A traffic spike exhausts reserved capacity. Instead of routing lower-risk tasks to a smaller model or queueing bounded work, requests fail outright.

What teams usually get wrong

  • Using retries as the capacity strategy.
  • Failing over without checking task compatibility.
  • Treating every request as equally important.
  • Hiding degradation from downstream evaluation.

What I would put in production

  • Define model routing tiers by task risk and capability.
  • Use bounded queues, admission control and concurrency limits.
  • Configure tested fallback models for eligible tasks.
  • Preserve high-risk work for the stronger model or human path.
  • Record which model actually handled every run.

What I would monitor

capacity saturation
fallback activation rate
queue age
quality by serving model
Takeaway: Graceful degradation has to be designed before capacity disappears.

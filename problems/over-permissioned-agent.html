Safety & Security

⚿ The agent can do much more than the task requires

A harmless model mistake becomes a serious incident when the runtime gives the agent broad authority.

What it looks like

  • A support agent can issue refunds far above the normal limit.
  • A read-heavy assistant also holds write or delete permissions.
  • One compromised tool token unlocks multiple unrelated systems.

Why this happens

Teams often begin with broad permissions because they make prototypes move quickly. In production, those permissions become the blast radius. The model does not need to be malicious; a misunderstood instruction, prompt injection, stale context or wrong tool choice is enough. If authorization is checked only when the session starts, a long-running agent may keep privileges after the user's role or the task risk has changed.

A simple real-world example

A customer-service agent needs to look up an order and create a refund request. The easiest integration gives it the same service account used by operations, which can refund any amount and cancel orders. A user asks for a $40 refund, but a prompt-injected note in the CRM convinces the agent to cancel the entire order. The dangerous part is not the sentence the model generated. It is that the runtime allowed the action.

What teams usually get wrong

  • Using one service account for every agent and every tool.
  • Treating tool visibility as authorization.
  • Checking permissions only at login instead of at action time.
  • Using a human approval prompt without enforcing the approval in the runtime.

What I would put in production

  • Give each agent only the capabilities needed for the current task.
  • Separate read, propose and execute permissions.
  • Re-check authorization at the moment of side effect.
  • Use amount, tenant and resource-level limits—not only role names.
  • Put irreversible or high-impact actions behind explicit policy and approval gates.

What I would monitor

denied action rate by tool
privilege use outside normal task paths
high-risk action volume
service-account scope drift

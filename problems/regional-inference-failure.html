Reliability & Runtime

◫ One inference region failed. Traffic kept going there.

A multi-region model deployment is not resilient if the router keeps sending requests to an unhealthy endpoint.

What it looks like

  • Only a portion of model requests return 5xx or timeout errors.
  • Healthy regions still have capacity, but user failures continue.
  • Removing one endpoint from routing immediately improves success rate.

The failure boundary

The model may be healthy in five regions and broken in one; the failure becomes product-wide only when routing cannot distinguish those states quickly enough.

Why this happens

Static round-robin pools spread traffic, but they also spread regional failures. Model gateways need active health, failure-rate windows and enough spare capacity to eject a bad region without overloading the survivors.

A production-shaped example

An AI service uses six inference regions. One region starts returning 503s after a provider-side routing change. Five regions remain healthy, yet one-sixth of traffic continues failing because the endpoint stays in the pool until someone changes configuration manually.

What fooled the team

  • Calling a deployment 'multi-region' without testing regional evacuation.
  • Using DNS reachability as the only health signal.
  • Immediately returning a recovered region to full traffic.
  • Running every healthy region near capacity, leaving no room for failover.

Prevent

  • Route through a model gateway with per-region health state and endpoint ejection.
  • Reserve failover headroom instead of operating every region at saturation.
  • Use region-specific circuit breakers and bounded retry policies.
  • Keep provider and deployment configuration versioned and centrally observable.

Detect

  • Break down success rate, 5xx, latency and throttling by region/deployment.
  • Run synthetic inference probes independent of user traffic.
  • Compare router decisions with endpoint health and capacity.

Recover

  • Eject the unhealthy region automatically after a bounded failure threshold.
  • Shift traffic only to regions with confirmed capacity.
  • Reintroduce the region gradually with canary traffic after recovery.

Prove it with failure injection

  • Force one region to return 503 while production-like traffic is flowing.
  • Simulate one slow region rather than a clean outage.
  • Recover the region and verify controlled re-entry rather than an immediate traffic flood.

What I would monitor

success rate by region
endpoint ejections
healthy capacity headroom
retry amplification
regional re-entry failures

Production invariant

Loss of one inference region must not become loss of the AI product when healthy capacity still exists.
Takeaway: Redundancy is inventory. Resilience is the ability to stop sending work to the broken copy.

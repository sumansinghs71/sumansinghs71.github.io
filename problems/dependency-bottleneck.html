Reliability & Runtime

DB The model was fast. A downstream dependency made the AI look slow.

Database locks, bad query plans and other dependencies can dominate end-to-end latency while model telemetry stays healthy.

What it looks like

  • Model latency remains normal while total request latency climbs.
  • Multiple AI features slow down at the same time.
  • Killing a blocking database session or changing a query plan restores performance immediately.

The failure boundary

Users experience one AI request, but the critical path crosses model, retrieval, databases, tools and network dependencies. The slowest layer owns the experience.

Why this happens

AI observability is often model-centric. That makes it easy to over-investigate tokens, context and provider latency while a conventional dependency is holding locks or running a pathological plan.

A production-shaped example

An agent service reads prompt/configuration metadata before every model call. A blocking database session holds a hot table lock. The LLM responds quickly once invoked, but most requests spend their time waiting before inference even starts.

What fooled the team

  • Using model latency as a proxy for user latency.
  • Looking at service averages instead of critical-path spans.
  • Restarting AI workers when the bottleneck is shared infrastructure.
  • Ignoring database plan changes because the application code did not change.

Prevent

  • Instrument end-to-end traces with separate spans for model, retrieval, DB, tools and queue wait.
  • Set dependency-specific timeouts and bulkheads.
  • Use appropriate indexes and query-plan controls for critical metadata paths.
  • Keep expensive administrative/reporting work away from latency-sensitive paths.

Detect

  • Monitor lock waits, connection-pool saturation, query-plan changes and DB time inside AI traces.
  • Compare model-service time with total user latency.
  • Alert on dependency contribution, not only total latency.

Recover

  • Remove the blocking workload or force a known-good query plan where appropriate.
  • Degrade non-critical reads if safe.
  • Drain queued work gradually after the dependency recovers.

Prove it with failure injection

  • Inject DB latency and lock contention.
  • Change a query plan in staging and compare critical-path traces.
  • Exhaust the connection pool while inference remains healthy.

What I would monitor

dependency time share
DB lock wait
connection-pool saturation
query-plan changes
model-vs-end-to-end latency delta

Production invariant

Every user-visible AI latency regression can be decomposed into owned time across the full critical path.
Takeaway: An AI system is still a distributed system. Sometimes the least glamorous dependency is the one users are waiting on.

DependenciesProduction failure pattern

DBThe LLM was fast. The AI request was waiting on SQL.

Model telemetry can stay green while locks, plans, pools or queues dominate the user's end-to-end latency.

request→DB wait 4.8s→LLM 0.7s→tool 0.3s
The model is only one span on the critical path.
Signals in production
  • Model latency is normal while total request latency climbs.
  • Several AI features slow down together.
  • Fixing a DB lock/plan/pool restores performance without changing the model.
Failure boundary

The user sees one AI request, but the critical path crosses ordinary distributed-system dependencies before and after inference.

01

Why it happens

AI observability often over-focuses on tokens and provider latency. That makes teams miss classic bottlenecks such as lock contention, connection-pool saturation, bad query plans, queue wait or a slow downstream API.

02

Production-shaped example

An agent reads prompt/config metadata before every model call. A blocking DB session holds a hot table. Inference itself is fast, but most user time is spent waiting before the model is even invoked.

What fooled the team
model latency = user latencyservice averages instead of critical-path spansrestarting AI workers for a shared DB bottleneck
First 5 minutes
  1. Open one slow trace and account for every millisecond by span.
  2. Inspect DB lock waits, pool saturation and plan changes before tuning the LLM.
  3. Contain the blocking workload, then watch backlog drain rate.
03

Controls

Prevent the failure, detect it early, then recover without making it worse.

PREVENT
  • Instrument separate spans for queue, DB, retrieval, model and tools.
  • Set dependency-specific timeouts/bulkheads and bounded pools.
  • Protect latency-sensitive paths from heavy administrative workloads.
  • Track and review query-plan/index changes on critical metadata paths.
DETECT
  • Compare model time with total request time.
  • Monitor lock waits, pool saturation and queue wait inside AI traces.
  • Alert on dependency contribution to latency, not only total latency.
RECOVER
  • Remove blocking work or restore a known-good plan when appropriate.
  • Degrade non-critical reads if the product can do so safely.
  • Drain queued work gradually after recovery.
Prove it with failure injection
  • inject DB latency
  • hold a lock on a hot path
  • exhaust connection pool
  • change query plan while LLM remains healthy
Monitor
DB wait sharelock waitpool saturationqueue agemodel vs end-to-end delta
PRODUCTION INVARIANTEvery AI latency regression can be decomposed into owned time across the full critical path.

An AI system is still a distributed system; the model is not always what the user is waiting on.

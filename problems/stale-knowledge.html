Knowledge & RAG

⌛ The new document exists, but the agent still answers from the old one

Knowledge freshness can fail between source update, ingestion, indexing, filtering and retrieval.

What it looks like

  • Users can open the new document, but the agent cannot find it.
  • Different tenants or regions see different versions of the same policy.
  • The correct answer appears only after an index rebuild or cache clear.

Why this happens

A RAG system has several clocks. The source system changes first. Ingestion notices later. Parsing and embedding take time. Index replicas may update at different moments. Caches can preserve old results after the index is fresh. If the application reports only 'last successful ingestion,' the team can miss freshness lag in the rest of the path.

A simple real-world example

Compliance publishes a new policy at 9:00 AM. The connector syncs it at 9:05, but the vector index rebuild completes at 9:40. A semantic cache still serves yesterday's answer until 10:15. Every component is technically working, yet for more than an hour users receive outdated guidance.

What teams usually get wrong

  • Monitoring only whether ingestion jobs succeeded.
  • Assuming index timestamp equals source freshness.
  • Caching answers without tying them to source versions.
  • Mixing old and new document versions in retrieval.

What I would put in production

  • Track source version through ingestion, parsing, embedding and index publication.
  • Expose end-to-end freshness lag, not just job status.
  • Invalidate caches when authoritative source versions change.
  • Prefer latest-version filters when documents supersede older copies.
  • Create freshness-sensitive evals for policies, prices and operational data.

What I would monitor

source-to-index freshness lag
queries served from superseded documents
cache age
version-mismatch rate

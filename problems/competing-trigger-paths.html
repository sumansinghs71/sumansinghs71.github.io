Tools & Integrations

⚡ A new trigger created a second execution path

Two individually valid consumers can become one duplicate-processing bug when ownership is ambiguous.

What it looks like

  • The same event is handled twice by different paths.
  • A webhook reacts immediately while a scheduled poller later sees altered state.
  • Disabling either path makes the issue disappear.

Why this happens

Adding a webhook, poller, queue consumer or cron job changes ownership semantics. Without a single claim/deduplication boundary, multiple components can believe they own the same unit of work.

A simple real-world example

An inbox workflow is normally processed by a scheduled poller. A new webhook is added for faster response. Both observe the same message, and each can trigger the agent before either has durably claimed the work.

What teams usually get wrong

  • Assuming faster triggers can simply be layered on top.
  • Using “unread” or another mutable business field as the only lock.
  • Deduplicating only inside one consumer.
  • Renewing subscriptions automatically without checking ownership.

What I would put in production

  • Define one authoritative ownership/claim boundary.
  • Use stable event IDs and idempotency across every trigger path.
  • Persist claims before side effects.
  • Make competing consumers observable in traces.
  • Chaos-test simultaneous delivery through multiple paths.

What I would monitor

duplicate event claims
same-event multi-consumer rate
dedupe hits
orphaned claims
Takeaway: Before adding another trigger, decide who owns the work.

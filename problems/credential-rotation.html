Safety & Identity

⌁ Security rotated the credential. The running agent kept the old one.

Credential rotation improves security, but long-lived workers fail if identity is loaded once and treated as permanent.

What it looks like

  • A previously healthy tool suddenly returns authentication failures after a planned rotation.
  • Restarting or reloading the worker fixes the issue.
  • Only long-running agents fail while newly started workers succeed.

The failure boundary

The external identity changed while the agent process stayed alive. A secret file update is not enough if the running process never refreshes what it already loaded.

Why this happens

Agents can live much longer than ordinary request handlers. They may cache passwords, tokens or secret-derived clients for hours. Rotation creates two versions of reality: the secret manager has the new credential while the process still holds the old one.

A production-shaped example

An overnight data agent authenticates successfully at startup. A scheduled credential rotation happens two hours later. New processes use the updated credential, but the long-running worker keeps reusing the stale client and every API call begins failing.

What fooled the team

  • Assuming updating a secret store automatically updates process memory.
  • Treating all 401/403 responses as permanent authorization denial.
  • Embedding credentials in static configuration.
  • Restarting the whole platform as the normal rotation strategy.

Prevent

  • Prefer short-lived credentials or workload identity where possible.
  • Read secrets through a version-aware provider instead of static config.
  • Refresh before expiry and on classified authentication failure.
  • Design client/session recreation without restarting the whole workflow.

Detect

  • Expose credential version/lease age without logging the secret.
  • Correlate auth failures with rotation events.
  • Alert when running workers hold a superseded credential version.

Recover

  • Invalidate the stale client and fetch the latest credential.
  • Retry only after identity refresh and within a bounded policy.
  • Checkpoint long-running work so auth recovery does not restart the job from zero.

Prove it with failure injection

  • Rotate credentials while a long-running task is active.
  • Revoke the old credential immediately and verify refresh.
  • Simulate secret-manager unavailability during rotation.

What I would monitor

credential age/version
refresh failures
auth errors after rotation
workers on superseded versions
workflow resumes after re-auth

Production invariant

A running agent must be able to survive authorized identity rotation without manual restart or use of stale authority.
Takeaway: Secret rotation is not complete when the vault changes. It is complete when every live consumer converges.

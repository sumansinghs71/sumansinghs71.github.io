IdentityProduction failure pattern

⌁The credential rotated. The running agent did not.

A valid security rotation can break long-lived agents that cache identity once and never refresh it.

agent process→cached cred v1→secret store→current cred v2
The vault changed. Process memory did not.
Signals in production
  • A healthy tool suddenly starts returning auth failures after rotation.
  • Restarting the worker fixes the problem.
  • New workers succeed while old workers fail.
Failure boundary

The secret/identity source has moved to version N+1 while a live process still holds version N.

01

Why it happens

Long-running agents can outlive passwords, tokens and client sessions. Updating the secret store does not mutate objects already loaded into a process. Rotation needs a convergence path for live consumers.

02

Production-shaped example

An overnight job authenticates at startup. Credentials rotate two hours later. New workers use the new version, but the existing worker keeps reusing a stale client and every API call begins failing.

What fooled the team
assuming vault update == process updatetreating every 401/403 as permanent denialrestart as the normal rotation mechanism
First 5 minutes
  1. Correlate auth failures with recent rotation events.
  2. Compare credential-version metadata between failing and fresh workers without logging the secret.
  3. Invalidate/recreate the client and verify re-auth before retrying work.
03

Controls

Prevent the failure, detect it early, then recover without making it worse.

PREVENT
  • Prefer short-lived workload identity/credentials when possible.
  • Use a version-aware secret provider, not static startup config.
  • Refresh before expiry and on classified authentication failure.
  • Support client/session recreation without restarting the workflow.
DETECT
  • Expose non-secret credential version/lease age.
  • Alert on consumers using a superseded version.
  • Correlate rotation event → auth error → successful refresh.
RECOVER
  • Invalidate stale client state and fetch current identity.
  • Retry only after successful refresh within a bounded policy.
  • Checkpoint long-running work so re-auth does not restart from zero.
Prove it with failure injection
  • rotate during active job
  • revoke old credential immediately
  • concurrent refresh by many workers
  • secret store temporarily unavailable
Monitor
credential age/versionrefresh failuresauth errors after rotationsuperseded consumersre-auth recovery rate
PRODUCTION INVARIANTAuthorized credential rotation must not require manual worker restarts or leave live agents using stale authority.

Rotation is complete when live consumers converge, not when the vault changes.

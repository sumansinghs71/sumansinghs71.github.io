Safety & Security

🔒 The agent worked—but secrets ended up in prompts, traces or eval data

Observability can accidentally become a second data-exfiltration path if sensitive values are captured everywhere.

What it looks like

  • API tokens or credentials appear in tool-call logs.
  • PII shows up in traces copied to debugging or eval systems.
  • Production conversations are reused for testing without proper redaction.

Why this happens

Agent observability is intentionally rich: prompts, retrieved text, tool arguments, tool results, reasoning metadata and user context. That detail is useful for debugging, but it also multiplies the places where sensitive information can land. A system can secure the production database correctly and still leak data through traces, screenshots or evaluation artifacts.

A simple real-world example

A support agent reads a customer record that contains a temporary access token in a free-text note. The token is sent to the model, copied into the trace, exported into a regression dataset and later viewed by engineers who never had access to the original customer system. The operational workflow respected access control; the telemetry pipeline did not.

What teams usually get wrong

  • Logging every tool argument and response by default.
  • Redacting only the final user-visible answer.
  • Assuming observability vendors have the same data boundary as the source system.
  • Building eval datasets directly from raw production traces.

What I would put in production

  • Classify and redact sensitive fields before telemetry leaves the runtime.
  • Use allowlists for what is safe to log on high-risk tools.
  • Separate secure audit evidence from developer-debug traces.
  • Apply retention and access controls to traces and eval artifacts.
  • Test redaction with realistic nested JSON, files and model-generated copies.

What I would monitor

redaction failures
sensitive-field detections in telemetry
trace access anomalies
retention-policy violations

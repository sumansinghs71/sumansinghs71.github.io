Production problem

◷ The background agent crashed after three hours

Long-running agents fail differently because the user, worker and environment may all change before the task finishes.

What it looks like

  • A job restarts from the beginning after a worker crash.
  • Completed side effects run again after resume.
  • The agent wakes up with expired credentials or assumptions that are no longer true.

Why this happens

A chat request is short enough that process memory often feels like state. A background agent can run through deployments, worker restarts, credential expiry and external-system changes. If durable progress is not persisted outside the process, recovery becomes guesswork. Even with checkpoints, blindly resuming is unsafe because the world may have changed while the agent was down.

A simple real-world example

An agent reviews 10,000 vendor records overnight. It has processed 7,200 when the worker is terminated during a deployment. On restart, the runtime reloads checkpoint 7,200. But record 7,200 also triggered an external update just before the crash. If the system cannot prove whether that update completed, simply continuing can duplicate the side effect.

What teams usually get wrong

  • Keeping the whole task state in the worker process.
  • Checkpointing only model conversation history.
  • Assuming a saved step number proves side effects completed.
  • Reusing credentials and approvals that were valid hours ago.

What I would put in production

  • Persist durable workflow state and checkpoint versions.
  • Use leases and heartbeats so only one worker owns a task at a time.
  • Record action receipts and reconcile uncertain external actions.
  • Revalidate permissions, time-sensitive data and external state after resume.
  • Support explicit cancel, timeout and partial-result semantics.

What I would monitor

resume success rate
lost work after failure
duplicate effects after resume
stale credential failures
checkpoint age

Reliability & Runtime

↔ The next message landed on another worker—and the conversation disappeared.

Session affinity can hide state design problems until traffic crosses workers, zones or regions.

What it looks like

  • Follow-up questions are treated as new conversations.
  • The issue appears intermittently or only after scaling/failover.
  • A single-node environment works perfectly while multi-node production loses context.

The failure boundary

If conversation correctness depends on process-local memory, any routing change becomes a semantic failure.

Why this happens

Sticky sessions can keep requests on one worker, but they are not durable state. Workers restart, regions fail and autoscaling moves traffic. Sequence numbers, conversation state and control flags need a shared source of truth if the workflow requires continuity.

A production-shaped example

A user asks a follow-up question. The load balancer sends it to a different data centre whose worker has no in-memory history for that conversation. The model receives a valid request—but without the prior turns needed to interpret it.

What fooled the team

  • Using stickiness as the only persistence mechanism.
  • Assuming conversation ID alone means the state exists everywhere.
  • Failing to version or sequence messages.
  • Testing only on one replica.

Prevent

  • Persist canonical conversation/workflow state outside the worker.
  • Use session affinity only as a latency optimization.
  • Carry a stable conversation ID plus monotonic sequence/version.
  • Make state reconstruction deterministic across workers and regions.

Detect

  • Log routing target, conversation version and state source for every turn.
  • Alert on sequence gaps, missing context and unexpected new-session creation.
  • Compare same-session requests across replicas.

Recover

  • Reload the latest durable state on a routing miss.
  • Reject or reconcile stale/out-of-order updates rather than silently overwriting newer state.
  • Rebuild transient caches from durable history.

Prove it with failure injection

  • Force every consecutive turn onto a different worker.
  • Restart the worker between two turns.
  • Replay out-of-order and duplicate messages.
  • Fail over between regions mid-conversation.

What I would monitor

context-miss rate
state reloads
sequence conflicts
cross-region session moves
conversation reconstruction latency

Production invariant

Any healthy worker that receives a valid conversation ID can reconstruct the state required to continue correctly.
Takeaway: Stickiness can improve locality. It should never be the thing preserving memory.

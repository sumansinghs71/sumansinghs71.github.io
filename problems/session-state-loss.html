Reliability & Runtime

🧵 The agent forgot the conversation after the next request

Session affinity can hide a state architecture problem until traffic moves to another worker or data centre.

What it looks like

  • Follow-up questions are treated as new conversations.
  • The problem appears only after scaling, failover or load balancing.
  • One worker remembers context while another does not.

Why this happens

Process memory is not durable conversation state. Sticky sessions can reduce symptoms, but if correctness depends on reaching the same host, failover and horizontal scaling remain fragile.

A simple real-world example

A user asks an agent to investigate an incident and then says “check the second service too.” The next request lands on another worker whose in-memory session is empty, so the agent loses the referent and starts over.

What teams usually get wrong

  • Calling sticky sessions a complete memory architecture.
  • Keeping sequence state only inside the model worker.
  • Letting missing conversation IDs silently create new sessions.
  • Failing to version concurrent updates to conversation state.

What I would put in production

  • Persist authoritative conversation/workflow state outside workers.
  • Use stable session and run identifiers end to end.
  • Apply optimistic concurrency or sequence checks for updates.
  • Treat affinity as an optimization, not a correctness requirement.
  • Test cross-worker and cross-region continuation.

What I would monitor

missing-context rate
session reassignment
sequence conflicts
cross-region resume success
Takeaway: If a request can move, the state required to understand it must move too.

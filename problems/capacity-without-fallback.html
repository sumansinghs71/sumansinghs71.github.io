Inference CapacityProduction failure pattern

↘The primary model hit capacity. The workflow had nowhere to go.

Quota and concurrency limits are normal. An outage happens when the system has no bounded degraded mode.

requests→primary SATURATED→admission→fallback / queue
Overload must become a policy decision, not a retry storm.
Signals in production
  • Failures rise only during traffic spikes.
  • Concurrency/token throughput reaches a provider or deployment limit.
  • Retries and backlog grow together.
Failure boundary

A bounded inference tier reaches capacity, but the runtime has only one admissible execution path.

01

Why it happens

Inference capacity is finite even when APIs feel elastic. Blind retries amplify pressure. A fallback model also changes behavior, so failover is safe only when the alternate path has workflow-specific eval coverage.

02

Production-shaped example

A morning burst exceeds the preferred model's concurrency allowance. Without admission control or a validated fallback, excess requests fail, retries multiply, and a queue grows faster than it can drain.

What fooled the team
immediate retries on throttlingassuming a smaller model is behaviorally equivalentan unbounded queue called 'graceful degradation'
First 5 minutes
  1. Confirm saturation vs application error using capacity telemetry.
  2. Stop retry amplification and protect critical traffic with admission control.
  3. Activate only a pre-tested fallback/degraded mode.
03

Controls

Prevent the failure, detect it early, then recover without making it worse.

PREVENT
  • Set explicit per-model concurrency/token budgets and priority classes.
  • Validate fallback models on workflow-specific golden/eval slices.
  • Bound queue size and queue age; propagate backpressure upstream.
  • Define degraded modes: lower-cost model, reduced scope, queued execution or human path.
DETECT
  • Track capacity utilization, throttle rate, queue age and retry volume.
  • Measure quality/tool-choice drift during fallback.
  • Separate overload from provider faults and application faults.
RECOVER
  • Shed/defer low-priority work first.
  • Route eligible work to validated capacity.
  • Drain backlog gradually after recovery.
Prove it with failure injection
  • lower primary capacity artificially
  • fallback model regression suite
  • backlog present during recovery
  • fallback itself reaches capacity
Monitor
capacity utilizationthrottlesfallback ratequeue agefallback quality delta
PRODUCTION INVARIANTCapacity exhaustion produces a bounded, intentional degraded mode—not an uncontrolled retry cascade.

Fallback is not a model name in config. It is a tested operating mode.

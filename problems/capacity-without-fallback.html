Model & Control Plane

↘ The primary model hit capacity. The workflow had nowhere to go.

Token, concurrency or quota pressure becomes a business outage when no degraded mode or validated fallback path exists.

What it looks like

  • Error rate rises sharply only during traffic spikes.
  • Requests exceed model concurrency, token or throughput limits.
  • Work falls back to manual handling because every overload request fails outright.

The failure boundary

Capacity failure is expected behavior from a bounded provider. The architectural failure is having only one admissible execution path when that bound is reached.

Why this happens

Inference capacity is not infinitely elastic. Dedicated capacity, shared quotas and model-specific limits can all saturate. Blind retries make pressure worse. Fallback must be designed before the incident—and validated because another model may behave differently.

A production-shaped example

An AI processing service normally uses a preferred high-capability model. A morning spike exceeds its concurrency allowance. With no admission control or compatible fallback, every excess request fails and a backlog forms faster than humans can absorb it.

What fooled the team

  • Treating overload as a transient error and immediately retrying.
  • Assuming a smaller model is automatically behaviorally compatible.
  • Failing open into an unlimited queue with no age or capacity policy.
  • Testing fallback only for response syntax, not task correctness.

Prevent

  • Use admission control and explicit per-model concurrency/token budgets.
  • Pre-register fallback models and validate them on workflow-specific evals.
  • Define degraded modes: lower-cost model, reduced context, read-only mode, queued execution or human path.
  • Keep queue size/age bounded and expose backpressure upstream.

Detect

  • Track quota utilization, concurrency, token throughput, throttling and queue age.
  • Distinguish provider overload from application bugs.
  • Measure quality and tool-choice drift when fallback activates.

Recover

  • Shed or defer low-priority work before critical work.
  • Route eligible tasks to validated fallback capacity.
  • Drain backlog at a controlled rate after capacity returns.

Prove it with failure injection

  • Artificially lower primary-model capacity and verify automatic degradation.
  • Run the same golden workflow suite on every fallback model.
  • Test recovery while a backlog already exists.

What I would monitor

capacity utilization
throttle rate
fallback rate
queue age
quality delta on fallback
manual spillover

Production invariant

A bounded model tier must produce a bounded, intentional degraded mode—not an uncontrolled outage.
Takeaway: Fallback is not a model name in config. It is a tested alternate operating mode.

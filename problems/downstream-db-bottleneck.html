Human & Operations

DB The AI was slow because the database was slow

Model latency is only one slice of end-to-end agent latency; ordinary distributed-system bottlenecks still dominate.

What it looks like

  • Users report slow AI responses while model latency is normal.
  • Several agent features degrade at the same time.
  • Database wait time or lock contention rises before LLM latency changes.

Why this happens

An agent is a distributed application. It still depends on databases, caches, queues, identity systems and external APIs. If observability starts at the model call, teams can spend hours tuning the wrong layer.

A simple real-world example

An agent loads prompt configuration and workflow state from a shared database. Blocking sessions hold locks on a hot table. The LLM responds quickly once called, but requests spend most of their time waiting before inference.

What teams usually get wrong

  • Looking at model p95 first for every AI latency incident.
  • Combining queue, DB, tool and model time into one latency number.
  • Restarting agent workers without locating the wait.
  • Ignoring query-plan or lock changes after releases.

What I would put in production

  • Trace queue → state store → retrieval → model → tools separately.
  • Expose DB wait, lock and pool saturation alongside model metrics.
  • Set dependency-specific SLOs and budgets.
  • Correlate latency changes with deployments and query-plan changes.
  • Build synthetic paths that exercise the whole workflow.

What I would monitor

end-to-end vs model latency
DB wait/lock time
connection-pool saturation
dependency contribution to p95
Takeaway: An AI system is still a system. Trace the whole critical path.

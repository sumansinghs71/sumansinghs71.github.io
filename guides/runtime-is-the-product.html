Teaching thread · Modern Agent Runtime

The runtime is becoming the product

Two teams can use the same model and build very different systems. The difference is usually not another clever prompt. It is what surrounds the model: which context it gets, what it can execute, how state survives, what gets verified and how failures are recovered.

30-second idea: Model quality matters, but production behavior increasingly comes from the harness around it: policy, state, tools, evidence, recovery and control.

The model proposes

A model output is a proposal: a tool name, arguments, a plan or a piece of code. Treating that proposal as an instruction to production collapses reasoning and authority into one layer. A stronger runtime validates and mediates the proposal.

The harness creates repeatable behavior

Prompts alone are difficult to govern at scale. Typed tools, policy checks, state machines, sandbox boundaries, budgets, retries and verifiers make behavior more predictable because they turn fuzzy intentions into explicit system rules.

Agents need to read their environment

A production agent should be able to inspect the evidence it needs—logs, traces, tool outcomes and relevant runtime state—without receiving unrestricted access to everything. Better observability can improve both human diagnosis and agent self-correction.

Control moves above individual agents

Once you run many agents, identity, budgets, versions, policies, kill switches and fleet-wide visibility become a control-plane problem. That is the point where 'an agent feature' becomes platform infrastructure.

Validated plans
Typed tools

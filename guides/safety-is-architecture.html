Teaching thread · Safety & Security

Safety is architecture, not a system prompt

A safe agent is not a model that says the right things. It is a system that makes unsafe actions difficult to execute even when the model is confused, manipulated or simply wrong.

30-second idea: Prompt injection, permissions, data boundaries, approvals, rollback and kill switches form one control system.

Start with the action, not the prompt

The most important question is not 'can someone jailbreak the model?' It is 'what can a bad or mistaken instruction cause the runtime to do?' A summarization error is annoying. A deletion, payment or data export is a different class of risk. That is why blast radius comes before model cleverness.

Separate decision from authority

The model can propose a tool, amount or target. The runtime should decide whether that action is allowed for this user, this task and this moment. Read, propose and execute are different capabilities. Keeping those capabilities separate makes both debugging and governance much clearer.

Approval is only one layer

Human review helps when judgment is genuinely needed, but it is not a replacement for authorization, validation or rollback. Approvals should bind to the exact action being reviewed, expire when important state changes, and sit inside a system that still enforces hard limits.

Design for the day the model is wrong

Production safety gets easier to reason about when you assume a bad decision will eventually happen. Then the architecture question becomes concrete: can we block it, limit it, detect it, undo it, and explain it afterward?

The production pattern

Minimize capability
Validate outside the model
Re-check authorization at execution
Require risk-based approval
Record an audit trail
Support rollback or kill

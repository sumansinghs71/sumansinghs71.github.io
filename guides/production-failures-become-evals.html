Teaching thread · Evals & Agent DevOps

Every useful production failure should become an eval

Evals become much more valuable when they are connected to operations. A production failure is evidence that your current test set did not protect a behavior that matters. The next release should not be able to rediscover the same failure for free.

30-second idea: The best regression set is not invented once. It grows from the failures your real system actually produces.

Capture the failure before fixing it

Save the input, relevant context, tool trajectory, source versions, runtime configuration and expected outcome. If the only artifact is a screenshot of the wrong answer, the team will struggle to reproduce the bug after the environment changes.

Turn the incident into a regression case

The smallest useful eval reproduces the behavior that should not return. That might be a deterministic tool check, a retrieval recall test, a safety scenario or a human-reviewed outcome. Not every problem needs an LLM judge.

Test the fix against more than one case

A prompt tweak can repair the incident and quietly damage another slice. Run the candidate fix against the golden set, related failure clusters and negative controls before calling it an improvement.

Close the loop in production

After deployment, monitor the same signal that originally exposed the failure. An offline pass is evidence, not proof. The real loop is production → failure → eval → fix → release → production verification.

The production pattern

Capture trace + versions
Cluster similar failures
Add permanent regression case
Evaluate candidate fix
Canary release
Verify production signal

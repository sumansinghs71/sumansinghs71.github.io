Teaching thread · Runtime & Reliability

Long-running agents are operations systems

A five-second chatbot request can pretend process memory is state. A five-hour agent cannot. Deployments happen, workers die, credentials expire, approvals age and external systems change while the task is still alive.

30-second idea: Once work outlives the browser session, durability, ownership, credentials, checkpoints and replay safety become the architecture.

Persist progress outside the worker

If a new worker cannot reconstruct the task, you do not have durable execution. Conversation history alone is not enough. The runtime needs explicit workflow state, ownership, versions and durable records of external effects.

Resume is not replay

Loading checkpoint 7,200 tells you where the agent thought it was. It does not tell you whether the last payment, email or API update completed before the crash. Recovery has to reconcile uncertain side effects before continuing.

The world may change while the agent sleeps

Permissions can expire. A price can change. An approval can become stale. A resource can be deleted. On resume, the runtime should revalidate the assumptions that matter instead of blindly restoring a frozen mental state.

Ownership needs leases and cancellation

Background work needs an owner even when no user is watching. Leases, heartbeats, cancellation, timeouts and partial results are normal distributed-systems concerns—and they become agent concerns as soon as tasks become long lived.

The production pattern

Durable workflow state
Leases + heartbeats
Action receipts
Idempotent side effects
Checkpoint versions
Revalidate before resume
Cancel + timeout semantics

Day 14 — Tool Permission Design

Tool permissions decide what an agent is allowed to do, not what it is smart enough to do. Permissions should follow user identity, action risk and current context.

Simple example

A support agent can read orders for the signed-in user but cannot query another customer's records.

Trade-offs

  • Fine-grained permissions improve safety but add policy complexity.
  • Static service accounts are simple but often overpowered.
  • Approval can complement—not replace—authorization.

Production readiness checks

  • Authorize every tool call server-side.
  • Use short-lived scoped credentials.
  • Separate read and write capabilities.
  • Audit denied as well as allowed actions.
